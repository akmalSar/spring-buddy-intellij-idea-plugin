SpringRetryableWithTransactionalInspection
@Retryable combined with @Transactional causes duplicate side-effectsERROR
Detects methods annotated with both 
 @Retryable
and 
 @Transactional
. When a 
 @Transactional
method fails mid-transaction, Spring rolls back the current transaction. Spring Retry then catches the exception, waits/backoff, and calls the method again — starting a brand-new transaction. Any work that succeeded before the failure in the first attempt is already undone by the rollback, yet non-transactional side-effects (external API calls, file writes, message publishes) are not rolled back and will be executed again on each retry. This leads to duplicate side-effects, inconsistent state, and data loss. Safe alternatives: Move retry logic outside the transaction boundary (retry the service call, not the transactional method). Make the transactional method idempotent so retries are harmless. Use a saga/outbox pattern for external side-effects instead of doing them inside the retried transaction.

 @EnableRetry

 @Configuration
class to activate its proxy infrastructure; without it,

is silently ignored and no retry happens at runtime.
