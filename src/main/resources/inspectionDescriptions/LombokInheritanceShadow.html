Reports field shadowing and related issues in class inheritance hierarchies.

Subclass field shadows a parent field

When a subclass redeclares a field with the same name as a field in an ancestor class, Java creates two separate memory locations on the same object. Reads and writes through a parent-typed reference will silently access the parent's copy of the field, not the subclass copy.


public class BaseDto {
    protected String name;
}

public class SubDto extends BaseDto {
    private String name;  // shadows BaseDto.name
}

BaseDto dto = new SubDto();
dto.name = "Alice";       // sets BaseDto.name, NOT SubDto.name

Shadowing field with @Getter / @Setter

Lombok generates getters/setters for the shadowing field, but they are invisible when the object is accessed through the parent type — the generated methods belong to the subclass, while parent-typed references resolve to the parent's field. Remove the field redeclaration and annotate the parent field instead.

@AllArgsConstructor on subclass with shadowed fields

{@code @AllArgsConstructor} on a subclass only covers the subclass's own fields. Shadowed parent fields will silently remain {@code null} after construction because the generated constructor does not know about them.

Validation annotation on a shadowing field

Bean Validation annotations ({@code @NotNull}, {@code @NotBlank}, {@code @Min}, {@code @Max}, {@code @Pattern}, {@code @Valid}, etc.) on a shadowing field will not fire when the object is validated through a parent-typed reference. The constraint is effectively invisible to the validation framework in that case.
