Reports dangerous or incorrect usage of {@code @EqualsAndHashCode} and {@code @Data} in the context of JPA entities and class hierarchies.

@EqualsAndHashCode without callSuper=true on a subclass

By default {@code @EqualsAndHashCode} only considers fields declared in the current class. On a subclass this silently excludes all inherited fields from equality checks. Two objects that differ only in parent fields will incorrectly be considered equal. Set {@code callSuper = true} to include parent fields.


// Warning — parent fields excluded
@EqualsAndHashCode
public class SubDto extends BaseDto { ... }

// Correct
@EqualsAndHashCode(callSuper = true)
public class SubDto extends BaseDto { ... }

@Data on a subclass

{@code @Data} implies {@code @EqualsAndHashCode} without {@code callSuper = true}, silently excluding parent fields from equality. Use explicit {@code @EqualsAndHashCode(callSuper = true)} and {@code @ToString(callSuper = true)} instead of {@code @Data}.

@EqualsAndHashCode on a JPA @Entity

Lombok-generated {@code equals()} and {@code hashCode()} using mutable fields breaks JPA entity identity, Hibernate session tracking, and collection behavior (e.g. {@code Set} membership). Entities should implement {@code equals()}/{@code hashCode()} manually using only the entity's stable identifier (e.g. the database-generated primary key) or a business key.


@EqualsAndHashCode  // breaks JPA — uses mutable fields
@Entity
public class User { ... }

// Correct — manual equals/hashCode on stable identifier
@Entity
public class User {
    @Id private Long id;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        return id != null && id.equals(((User) o).id);
    }

    @Override
    public int hashCode() {
        return getClass().hashCode();
    }
}
